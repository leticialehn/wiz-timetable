## Story

**As a** secretaria on `/admin/comercial`,
**I want** a "Remover" button next to "MATRICULADO" for each prospect,
**so that** I can take a prospect who isn't coming back off the list,
without needing to go find and delete each of their occurrences in the
grid one by one.

## Request (owner, 2026-09-23)

> "Otimo. Agora na aba do comercial, ao lado de matriculado, quero que
> apareça remover também."

## Acceptance Criteria

1. Each prospect row has a "Remover" button next to "MATRICULADO" (hidden
   while that row's own "MATRICULADO" form is open, matching the existing
   `matriculando !== a.nome` pattern).
2. Clicking it asks for confirmation (mentions the prospect's name and how
   many occurrences will be deleted) before doing anything irreversible.
3. Confirming deletes **every** occurrence behind that grouped prospect
   name — a `Lead` is a name-grouped aggregation of possibly-several
   avulso bookings (different days/professoras/weeks), not a single DB
   row, so "remove the prospect" means removing all of them.
4. Reuses the grid's own `removerCelula` server function (already
   secretaria-only, already handles both `grade_base`-origin and
   `excecoes_semana`-origin rows correctly) — no new server function,
   consistent with how Story 7.3 also reused an existing function
   (`criarAluno`) rather than inventing a new one.
5. `npm run typecheck`, `npm run lint`, `npm test` all pass.

## Dev Notes

- **Why loop `removerCelula` instead of a new bulk-delete-by-name
  function?** A name-based bulk delete (`WHERE aluno_nome_avulso ILIKE
...`) would have to reimplement the same normalized-name-matching logic
  `agruparOcorrenciasPorNome` already uses to group occurrences in the
  first place (accent/case variants) — risking a mismatch between what
  the UI _displays_ as one prospect and what a fresh query _deletes_.
  Looping the already-computed `lead.ocorrencias` (each with an exact row
  id) guarantees the delete matches exactly what's on screen, and reuses
  `removerCelula`'s existing secretaria-only auth gate instead of adding
  a second one.
- **`escopo:"base"` for `origem==="base"` occurrences**: intentional full
  delete, not the "just this week" exception path `removerCelula` also
  supports for real alunos in the grid. A Comercial/experimental prospect
  being removed here means "not coming back," not "not coming this
  specific week."
