## Story

**As a** secretaria/professora using the grade screen with multiple people editing at once,
**I want** changes made by one person to show up live for everyone else without a manual
refresh,
**so that** the weekly grid, presence, and lesson data stay in sync during class hours —
without reopening the public read/write hole that Story 2.1 just closed.

## Acceptance Criteria

1. A written decision is recorded (in `docs/DB-AUDIT.md` §3, replacing the current "🟠
   Realtime is partially broken" note) comparing the three options from
   `EPIC-002-db-reconciliation.md` AC6: (a) narrow `SELECT USING (true)` policies +
   `GRANT SELECT` per table, (b) drop Realtime for that table and poll/manually
   refresh instead, (c) authenticated Realtime with a request-scoped client.
2. The decision treats tables differently by sensitivity, not as one blanket choice:
   - Low-sensitivity (schedule/config, no PII): `professoras`, `grade_base`,
     `horarios_config`, `excecoes_semana`.
   - High-sensitivity (PII of minors / grades / attendance): `alunos`,
     `aulas_presenca`, `aulas_notas`.
   - `aulas_licoes` is out of scope — it already has a deliberate, documented public
     `SELECT` policy (see `docs/DB-AUDIT.md` §0/§3) and keeps it as-is.
3. Option (c) (authenticated Realtime) is evaluated honestly against this app's actual
   auth: it's a custom cookie-session system (`usuarios`/`usuario_papeis` +
   `auth.server.ts`), not Supabase Auth — the browser Supabase client only ever holds
   the anon key, never a per-user Supabase session/JWT. If (c) is picked, the story
   must implement whatever is needed to give the browser client an authenticated
   Supabase session (or explicitly document why that's out of scope and pick (a)/(b)
   instead for now).
4. The decision is implemented:
   - For each low-sensitivity table: either a new migration adding
     `GRANT SELECT ... TO anon` + a narrow `SELECT USING (true)` policy (option a), or
     `src/hooks/use-realtime-grade.ts` stops subscribing to it and the relevant
     screens get a polling/manual-refresh fallback (option b).
   - For each high-sensitivity table: default to option (b) unless the decision in
     AC1 explicitly justifies (a) or (c) for that specific table with a stated
     reason.
5. `src/hooks/use-realtime-grade.ts` (`TABELAS` array) matches exactly what's decided
   — no table is left subscribed if its access was intentionally dropped, and no
   table is left un-subscribed if it was intentionally re-granted.
6. If any new `GRANT`/policy is added: verified live with the real anon key
   (`VITE_SUPABASE_PUBLISHABLE_KEY`) that it allows `SELECT` only — no `INSERT`,
   `UPDATE`, or `DELETE` — matching the pattern already established in
   `supabase/migrations/20260917103416_relock_public_tables.sql` and
   `20260917110000_revoke_default_privileges_anon.sql`.
7. `docs/DB-AUDIT.md` §3 (RLS & GRANT matrix) and §6 (priority checklist) are updated
   to reflect the final state, same as Story 2.1 did.
8. No credentials committed; every schema change is a migration (per the "no Studio
   edits" rule Story 2.1 established) — `supabase migration list` clean after.

## Dev Notes

- No `architecture/` docs exist in this repo beyond `docs/architecture.md` and
  `docs/DB-AUDIT.md` — those are the only sources of truth here; there is no
  `frontend-architecture.md` / `data-models.md` to cross-reference. This note
  replaces the "No specific guidance found" fallback the task template expects.
- **Current Realtime wiring**: `src/hooks/use-realtime-grade.ts` subscribes to
  `postgres_changes` on `professoras`, `alunos`, `grade_base`, `horarios_config`,
  `excecoes_semana`, `aulas_presenca`, `aulas_notas`, `aulas_licoes` (8 tables) using
  the browser's anon-key Supabase client (`src/integrations/supabase/client.ts`), and
  calls `queryClient.invalidateQueries()` (no filter — invalidates everything) on any
  event from any of them.
- **Why most of these currently don't fire**: as of Story 2.1's QA pass
  (2026-09-17), `anon`/`authenticated` GRANT + all public policies are revoked on 7 of
  these 8 tables (`aulas_licoes` is the deliberate exception with a public
  `SELECT USING (true)` policy for exactly this reason). Supabase Realtime only
  delivers a `postgres_changes` event to a subscriber if that subscriber's role can
  `SELECT` the row per RLS — so today, only `aulas_licoes` changes actually reach the
  browser; the other 7 are silently dead. [Source: docs/DB-AUDIT.md §3, as updated by
  Story 2.1]
- **Auth model**: this app does NOT use Supabase Auth. Login is a custom
  cookie-session system — see `src/lib/auth.server.ts` (`usuarioDaSessao`,
  `requireAuthenticated`, `requireRole`) backed by the `usuarios`/`usuario_papeis`
  tables. The browser's Supabase client only ever authenticates as `anon`. This is
  why option (c) (authenticated Realtime) is not a drop-in — there is no Supabase
  session to hand it.
- **Sensitivity of the 7 affected tables** (from `docs/DB-AUDIT.md` §1/§4):
  `alunos` carries PII of minors (nome, nascimento, contrato, créditos);
  `aulas_presenca`/`aulas_notas` carry attendance/grades tied to named students.
  `professoras`, `grade_base`, `horarios_config`, `excecoes_semana` carry schedule/
  config data with no student PII.
- **What Story 2.1 already established as the working pattern** for adding any new
  public grant/policy safely: `supabase/migrations/20260917103416_relock_public_tables.sql`
  and `20260917110000_revoke_default_privileges_anon.sql` show the exact style
  (explicit table list, `SELECT`-only where public access is warranted, verified live
  against prod with the real anon key by creating/dropping a throwaway table or
  querying with the anon client directly). Follow the same verification discipline
  here — don't just trust the SQL, prove it against prod like those two migrations
  did.
- **Package versions**: `@supabase/supabase-js` `^2.110.1`, `react` `^19.2.0`
  (from `package.json` — relevant if AC3's authenticated-Realtime path is chosen and
  needs an SDK feature check).
