## Story

**As a** developer making future schema changes,
**I want** `supabase/migrations/` to reproduce the exact production schema,
**so that** I can branch/test/reset the database safely and reviewers can see the
real starting point.

## Acceptance Criteria

1. `supabase db pull` is run against the production project and its output committed
   as `supabase/migrations/<timestamp>_baseline_from_prod.sql`.
2. `supabase migration list` shows **no drift** (local == remote) after the baseline
   is applied/repaired.
3. The baseline (or explicit follow-up migrations) contains DDL for the previously
   untracked objects: `aulas_licoes`, `calendario_excecoes`, `alertas_status`,
   `alunos.data_inicio_nivel`, `alunos.data_nascimento`.
4. The real UNIQUE constraint on `aulas_presenca` and `aulas_notas` is captured
   verbatim (verify whether it includes `parte` / `horario_especifico`).
5. `src/integrations/supabase/types.ts` is regenerated and matches.
6. A short note is added to `docs/DB-AUDIT.md` recording what was found vs. the old
   migration history, and `README`/`CONTRIBUTING` states "schema changes via migration
   only — no Studio edits".
7. No credentials (DB password, access token, service key) are committed.

## Dev Notes

- `supabase/config.toml` exists. The project has 12 tables (see `docs/DB-AUDIT.md`).
- Old migrations mutated CHECK constraints via anonymous `DO $$` blocks that look up
  the constraint name — the pull will materialise their final names; that's fine.
- `alunos` columns already in migrations: `situacao`, `contrato_inicio`,
  `contrato_fim`, `creditos`. Missing: `data_inicio_nivel`, `data_nascimento`.
- The lockdown migration (`20260812180211…`) is the security baseline for the DB
  layer (anon revoked). Preserve its effect in the new baseline.
- Coordinate timing: land this when no one has uncommitted local migrations.

### Testing

- `supabase db reset` on a **local/branch** database must apply the new baseline
  cleanly and end in a schema identical to prod (`supabase db diff` empty).
- Do not run `db reset` against production.
