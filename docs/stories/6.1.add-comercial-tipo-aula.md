## Story

**As a** secretaria,
**I want** a "Comercial" cell type with 4 fixed 15-minute slots per period,
**so that** I can schedule prospective clients for enrollment conversations without
occupying a real teaching seat or a book-tracked class slot.

## Acceptance Criteria

1. `TipoHorario` (`src/lib/types.ts`) gains `"comercial"`. `CAPACIDADE.comercial = 4`,
   `ROTULO_TIPO.comercial = "Comercial"`, `TIPO_MOSTRA_LIVRO.comercial = false`,
   `TIPO_FECHADO.comercial = false`. `TipoAula` (`Exclude<TipoHorario, "break" |
"preparacao_homework" | "sem_aula">`) picks it up automatically — do not add it to
   the exclusion list. **Found in PO validation (2026-09-17):** two more exhaustive
   `Record<TipoHorario, string>` color maps exist beyond these 4 — `tipoCardBg()` in
   `professora.tsx:1271` and the equivalent map in `admin.index.tsx:1032` — plus the
   CSS custom properties they reference (`--tipo-{tipo}-bg`/`-fg` in `src/styles.css`,
   e.g. `--tipo-conversacao-bg`). Both are `Record<TipoHorario, ...>` so TypeScript
   will fail to compile until `comercial` is added to both, which is a useful
   guardrail — but add a new `--tipo-comercial-bg`/`-fg` pair to `styles.css` too, or
   it'll compile with an empty/undefined color. Pick a color distinct from all 8
   existing tipos (a prospect slot should read as visually different from any real
   class type) — exact color is an implementation choice, not prescribed here.
2. A generalized `slotMinutosPorTipo: Partial<Record<TipoHorario, number>>` (or
   equivalent) replaces the hardcoded `20` inside `slotsOnlinePorPeriodo`, with
   `online: 20, comercial: 15`. Rename/refactor to a single
   `slotsFixosPorPeriodo(tipo, periodo)` that returns `[]` for tipos without fixed
   sub-slots, preserving `slotsOnlinePorPeriodo`'s existing output for `"online"`
   byte-for-byte (same strings, same order) — this is a refactor, not a behavior
   change for Online.
3. **Re-grounded 2026-09-17 — this is 5 call sites, not 1.** Every place in
   `src/routes/admin.index.tsx` that branches on `tipo === "online"` or calls
   `slotsOnlinePorPeriodo` directly is generalized to
   `slotsFixosPorPeriodo(tipo, periodo)` (or `.length > 0` where it's a boolean
   check), so "Comercial" gets the same fixed-slot-by-position behavior Online
   already has everywhere, with zero duplicated JSX/logic and no spot missed:
   - line ~471: the main cell-rendering branch (`if (tipo === "online")`) that maps
     each fixed slot to a `CelulaAula`/`LinhaVaziaEditavel`/`LinhaVagaTrancada`.
   - line ~837: `ehOnline` inside `LinhaVaziaEditavel`, which drives
     `precisaEscolherHorario` (whether the empty-cell form must ask which
     sub-slot before saving).
   - line ~985: the `<select>` options in that same form, built from
     `slotsOnlinePorPeriodo(periodo)` directly.
   - line ~1125/1139: `confirmarAdicao`'s validation (`"Escolha o horário do
slot"`) and the `horario_especifico` it sends to the server.
   - line ~1402/1411: the same tipo-gated `<select>` + `slotsOnlinePorPeriodo`
     call inside the "add to any period" search/modal flow.
4. Secretaria can configure a "Comercial" cell on any período/professora via the
   existing cell-type picker (`admin.index.tsx` line ~56's tipo list) — no new
   restriction beyond the `requireRole(["secretaria"])` guard every other cell-type
   edit already has (Story 1.3).
5. Booking a name into a Comercial slot uses the exact same free-text
   `aluno_nome_avulso` path every other avulso booking uses today (`grade.functions.ts`) — no
   new server function, no new DB column, no write to the `alunos` table.
6. **Database migration** (EPIC-002 is now Done — see Dev Notes for exactly which
   3 constraints and their current allowed values): a new, named migration file
   adds `"comercial"` to the CHECK constraints on `horarios_config.tipo`,
   `grade_base.tipo`, and `excecoes_semana.tipo`. Applied via `supabase db push`,
   verified with `supabase migration list` (no drift) — not a Studio edit, not an
   ad-hoc `DO $$` block.
7. **New (2026-09-17 re-grounding):** `src/routes/professora.tsx`'s
   `mostraNotasELicao = tipo !== "conversacao"` (line ~448) is a **blocklist**, not
   an allowlist — without a change, adding `"comercial"` to `TipoHorario` would
   make this default to `true` for Comercial cells, showing note/lição inputs for
   prospects who are never real matriculated students. Update the condition to
   also exclude `"comercial"` (mirroring how `"conversacao"` is already excluded).
8. `npm run typecheck` and `npm run lint` pass. Existing "Online" cells (both in
   the grid editor across all 5 generalized call sites, and the professora-facing
   view) render identically before and after the refactor — spot-check at least
   one populated Online cell in each view.

## Dev Notes

- **Re-grounded 2026-09-17 (the 2026-09-14 draft undercounted this — see below).**
- **Exact current mechanism:** `slotsOnlinePorPeriodo` (`types.ts:409-414`)
  hardcodes 20-minute offsets from `HORARIO_INICIO_PERIODO`. `admin.index.tsx` has
  **5 separate call sites** that branch on `tipo === "online"` or call
  `slotsOnlinePorPeriodo` directly — not 1 as the original draft said (re-checked
  by grep, confirmed by reading each): lines 471, 837, 985, 1125/1139, 1402/1411.
  See Tasks above for what each one does. Miss one and Comercial cells will
  half-work (e.g., render fixed slots correctly but never force a horário choice
  when booking through the "add to any period" modal).
- `professora.tsx:708`'s `ehOnline` (drives `mostraParte2/3/4`, i.e. whether a
  booking shows 2 lesson-part inputs by default) is a **different concern** from
  the admin-side sub-slot editor — it's about one already-booked row's own
  lição/nota inputs, not about splitting one cell into N sub-slots. It's gated
  behind `mostraNotasELicao` (see AC7) — since Comercial will be excluded from
  `mostraNotasELicao`, this whole block won't render for Comercial rows regardless
  of `ehOnline`'s value, so **it very likely needs no change**. Confirm this at
  implementation time rather than assuming — if it turns out `mostraNotasELicao`
  is checked in a different order somewhere, this could still matter.
- **`mostraNotasELicao` is a blocklist, not an allowlist** (`professora.tsx:448`,
  `tipo !== "conversacao"`) — found during this re-grounding. Every new
  `TipoHorario` value defaults to `true` here unless explicitly excluded. AC7
  covers adding the exclusion; without it, prospects would get note/lição input
  boxes on the professora screen, which makes no sense for a non-tracked booking.
- **The three CHECK constraints to widen** (source: `docs/DB-AUDIT.md` §5a,
  verified live against prod 2026-09-17, zero drift from the migration file):
  - `horarios_config_tipo_check`: currently `regular, online, break,
preparacao_homework, reforco, vip, conversacao, sem_aula` (8 values) → add
    `comercial` (9th).
  - `grade_base_tipo_check`: currently `regular, online, vip, reforco,
conversacao` (5 values) → add `comercial` (6th).
  - `excecoes_semana_tipo_check`: currently `NULL` or `regular, online, vip,
reforco, conversacao` (5 values + null) → add `comercial` (6th + null).
  - All three live in `supabase/migrations/20260915134213_baseline_from_prod.sql`
    — write a new migration, don't edit that file.
- **Booking mechanism confirmed already generic:** `grade.functions.ts`'s
  `aluno_nome_avulso` path (used by "Exp" experimentais today) requires no changes
  — Comercial bookings are just another avulso under a new `tipo`.
- **Do not touch:** `alunos` table/type, `requireRole` guard logic (Story 1.3),
  any other `TipoHorario`'s capacity/label/behavior.
- **Sequencing:** EPIC-002 is now fully Done (Stories 2.1-2.3, 2026-09-17) — the
  migration task is no longer blocked. No particular task ordering is required
  anymore; the "app code first, migration last" split from the original draft is
  no longer necessary, though still a reasonable way to work.
