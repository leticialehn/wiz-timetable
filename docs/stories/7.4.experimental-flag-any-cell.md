## Story

**As the** owner,
**I want** a walk-in doing an experimental class to never become a real
`alunos` row, and to be visually distinguishable to the professora, no
matter which cell (regular, Comercial, or otherwise) the secretaria types
their name into,
**so that** the bug Story 7.1 was supposed to close doesn't reopen just
because the natural, low-friction workflow (type a name into an
already-existing cell, check "avulso") never went through a
Comercial-typed cell in the first place.

## Root Cause

Story 7.1's fix only intercepted `criarAluno` when the **cell's own
`tipo`** (`horarios_config.tipo`, set for the whole
professora/período/dia_semana slot via the "⋯" advanced editor) was
`"comercial"`. But `tipo==="comercial"` requires a dedicated, empty slot —
it can't be mixed with real students already booked in a regular period.
The secretaria's actual workflow for a walk-in is to type the name into
whatever cell is already open (often a regular class period, alongside
real students) and check the simple "Avulso (só esta semana)" checkbox in
`LinhaVaziaEditavel`. That checkbox only ever controlled `escopo` (weekly
vs. permanent) — it never controlled whether a real `alunos` row got
created. So typing a new name there, checking "avulso", still always
called `criarAlunoFn`, reproducing the original bug for every cell type
except a dedicated Comercial one.

Confirmed live in production: `alunos` had a real row `"Aaaa"`
(`situacao='matriculado'`), booked via `excecoes_semana` with
`tipo='regular'` — not `'comercial'` — exactly matching this root cause.

## Story

**As a** secretaria adding a walk-in experimental student to any cell,
**I want** an "Experimental" checkbox separate from cell type,
**so that** I never have to reconfigure the whole period to Comercial just
to avoid accidentally creating a real aluno.

## Acceptance Criteria

1. `LinhaVaziaEditavel` (the primary inline "type a name" editor, used for
   every cell type) has an "Experimental (não é aluno ainda)" checkbox,
   shown whenever the cell isn't already Comercial-typed and no existing
   aluno was picked from the autocomplete.
2. Checking it and confirming a typed name: never calls `criarAluno`;
   books via `aluno_nome_avulso` (same free-text mechanism Comercial
   already used); forces `escopo="semana"` (never a permanent
   `grade_base` row); skips the nível requirement (the person isn't an
   enrolled aluno yet).
3. The booking row is written with `experimental=true` on
   `excecoes_semana` (pre-existing, previously-unused column from the
   production baseline schema — `boolean default false`, `excecoes_semana`
   only, no migration needed).
4. `getLeads`/`getProspectosComerciais` treat `experimental=true` the same
   as `tipo='comercial'` — an experimental walk-in shows up on
   `/admin/comercial` regardless of which cell type it was booked in, and
   never in the plain Leads list.
5. In the grid, a row with `experimental=true` is visually distinct
   (amber color + "🧪 experimental" badge) from a real student's row, even
   inside a regular-typed cell mixed with real students — directly
   answering the owner's "como a professora vai entender" question.
6. The server function rejects `experimental=true` combined with
   `escopo="base"` (a prospect can never become a permanent fixed slot).
7. `npm run typecheck`, `npm run lint`, `npm test` all pass.

## Dev Notes

- **Why not just require Comercial cells for all prospects?** Because
  `tipo` is set on the whole `horarios_config` slot
  (professora/período/dia_semana), not per booking — a period already
  hosting real students can't be reconfigured to Comercial without
  breaking their booking. An experimental walk-in joining an ongoing real
  class (the most realistic "experimental class" scenario) structurally
  cannot go through a dedicated Comercial cell. `experimental` is a
  per-row flag specifically so it can coexist with real students in the
  same cell.
- **The `experimental` column already existed, unused.** Found via
  `information_schema.columns` on `excecoes_semana` while investigating —
  `boolean default false not null`, added in the production baseline
  migration (`20260915134213_baseline_from_prod.sql`), predating this
  entire session's work. Grepping the codebase confirmed zero references
  anywhere in application logic before this story. This story is the
  first thing to actually wire it up.
- **Relationship to Comercial (`tipo==="comercial"`)**: kept orthogonal.
  A Comercial-typed cell's bookings are NOT also marked
  `experimental=true` (the `tipo!=="comercial"` guard in
  `handleCriarEAdicionar`) — `tipo==='comercial'` alone is already
  sufficient signal for that path; `experimental` exists specifically for
  the case `tipo!=='comercial'`. Both funnel into the same
  `getProspectosComerciais` list via the `OR` filter.
- **Not touched**: the "⋯" advanced `CelulaEditor` modal — already
  avulso-only for every tipo since before this session (confirmed during
  Story 7.1's investigation), never created a real aluno, so it was never
  part of this bug.
