# Story 5.2: Soft-delete for "Remover aluno" (replaces hard CASCADE delete)

## Status

Done

quality_gate_tools: [coderabbit, typecheck, lint]

## Story

**As a** secretaria who clicks "Remover" on a student,
**I want** that action to stop being an irreversible hard delete that erases their
entire attendance/grades/lição history,
**so that** removing a student from the active roster doesn't also destroy the
academic record — confirmed with the owner 2026-09-18: soft-delete is the wanted
behavior, not a hard delete.

## Acceptance Criteria

1. `removerAluno` (`src/lib/cadastros.functions.ts:162`) no longer runs
   `.from("alunos").delete()`. Instead it marks the aluno removed — `ativo =
false` plus a new `situacao` value (`"removido"`, distinct from the existing
   `"nao_rematriculado"`/`"cancelado"`, which both mean "finished/left, but the
   record stays a normal inactive aluno" — "removido" specifically means "taken
   off the roster via this action," see Dev Notes for why a new value is needed
   rather than reusing one).
2. `SituacaoAluno` (`src/lib/types.ts:27`) gains `"removido"`; `ROTULO_SITUACAO`
   gets a matching label (e.g. "Removido"). The `alunos_situacao_check` CHECK
   constraint (confirmed 3 current values: `matriculado`, `nao_rematriculado`,
   `cancelado` — `docs/DB-AUDIT.md` line 261) is widened via a new migration to
   accept the 4th value, same pattern as Story 6.1's `tipo` constraint widening —
   applied via `supabase db push`, verified with `supabase migration list`.
3. Every place that reads `alunos.ativo`/`alunos.situacao` to decide who counts
   as an active/inactive/matriculated student is audited (grep `\.ativo\b` and
   `\.situacao\b` across `src/`, don't rely on this story's list being
   exhaustive) and a decision made per call site: does "removido" belong with
   the other inactive statuses, or does it need its own explicit exclusion?
   Confirmed relevant so far: `admin.alunos_.inativos.tsx` (inactive list — a
   removido aluno should very likely still show here, not disappear entirely);
   `getRelatorioMatriculas`'s `alunosMatriculados` count
   (`relatorios.functions.ts:474`, re-confirmed in PO validation 2026-09-22 —
   was line 430 when originally drafted, shifted after Story 6.2 grew this
   file; re-check the line number again at implementation time, don't trust
   either number, currently `a.ativo && a.situacao ===
"matriculado"` — already excludes non-matriculado, so "removido" is already
   excluded here with no change needed, confirm this holds).
4. The "Remover" button's `confirm()` dialog text
   (`admin.alunos.tsx:474`) is updated to reflect the new, reversible-by-support
   behavior (no longer implies permanent, irreversible deletion) — exact wording
   is an implementation choice, not prescribed here.
5. No UI currently exists to reverse a "removido" status back to "matriculado" —
   **out of scope for this story** unless trivial to add via the same dropdown
   `admin.alunos_.inativos.tsx` already uses for `nao_rematriculado`/`cancelado`
   (confirm at implementation time whether that dropdown already supports
   arbitrary `SituacaoAluno` values or needs an explicit new option).
6. `npm run typecheck` and `npm run lint` pass; no regression to the existing
   `nao_rematriculado`/`cancelado` flows.

## Dev Notes

- **Grounded 2026-09-18** by reading `types.ts:24-33` (`SituacaoAluno` is a
  closed 3-value union, `ROTULO_SITUACAO` its label map),
  `cadastros.functions.ts:162-172` (`removerAluno`'s exact current `.delete()`
  call), `admin.alunos.tsx:474` (the `confirm()` call site), and
  `docs/DB-AUDIT.md` line 261 (the `alunos_situacao_check` constraint's exact 3
  current values) — none of this is inferred.
- **Why a new `situacao` value instead of just `ativo = false`**: `ativo` alone
  can't distinguish "left because they finished/cancelled" (existing
  `nao_rematriculado`/`cancelado`, which are meaningful business outcomes,
  already tracked by the rematrícula-alert flow) from "taken off the roster via
  the Remover button" (this story's new case) — collapsing them would make
  reports/alerts that key off `situacao` (e.g. `getRelatorioMatriculas`) treat a
  "removido" aluno the same as a normal graduated/cancelled one, which may not
  be intended. Confirm this reasoning holds once Task 3's audit is actually
  done — it's the story's own hypothesis, not a settled fact.
- **`admin.alunos_.inativos.tsx:94/127`**: confirmed both spots already derive
  `ativo: situacao === "matriculado"` when writing a situacao change from a
  dropdown — worth checking whether "removido" can just be added as another
  dropdown option there for Task 4's reversal path, rather than building new UI.
- **Owner decision (2026-09-18)**: soft-delete confirmed as the wanted behavior
  over keeping the hard delete — see EPIC-005's Risks section for why this
  needed an explicit decision rather than an engineering judgment call.
