## Story

**As a** data protection owner,
**I want** every server function that reads or writes school data to verify the
caller's session,
**so that** the RPC endpoints cannot be called directly to bypass the login screen.

## Acceptance Criteria

1. Every exported `createServerFn` in **all 8** data modules calls
   `await requireAuthenticated()` as the first statement of its handler (bare call is
   fine when the returned `usuario` is not needed):
   `alertas.functions.ts`, `cadastros.functions.ts`, `calendario.functions.ts`,
   `grade.functions.ts`, `historico.functions.ts`, `presenca.functions.ts`,
   `relatorios.functions.ts`, `usuarios.functions.ts`.
   Baseline count from `grep`: **39 endpoints** (see the pre-filled checklist in Dev
   Agent Record). If `grep` finds more at implementation time, guard those too and
   update the checklist.
2. `auth.functions.ts` is intentionally exempt: `login`, `logout`, `getSessaoAtual`
   stay public; `criarPrimeiroUsuario` keeps its existing "0 users" guard.
3. An unauthenticated call to any guarded endpoint fails with the existing
   `"Não autorizado. Faça login."` error and performs **no** DB read or write (guard
   is above the first `supabaseAdmin` / `sb()` call in every branch).
4. The checklist in Dev Agent Record is completed — every row `Done`, count matches
   the `grep` result.
5. The professora screens and admin screens still work end-to-end for a logged-in
   user (no over-guarding that breaks a legitimate flow).
6. `npm run typecheck` + `npm run lint` pass; pre-commit hook green.
7. **`usuarios.functions.ts` coordination:** after this story a logged-in `professor`
   could call `criarUsuario` / `removerUsuario` (auth-only, role check is Story 1.3).
   Either (a) ship 1.2 + 1.3 in the same PR, or (b) add
   `await requireRole(["secretaria"])` to the 5 `usuarios.functions.ts` endpoints in
   this story. Decide and record in Completion Notes; do not deploy 1.2 alone with
   `usuarios` endpoints only auth-gated.

`escola-auth` cookie flow) is already wired. Story 1.3 (role checks) should follow
immediately or share this PR (see AC7).

- `requireAuthenticated()` (in `src/lib/auth.server.ts`) calls `usuarioDaSessao()`,
  which reads the `escola-auth` session cookie and loads the user + papéis via
  service role; throws `Error("Não autorizado. Faça login.")` when there is no valid
  session. Returns `UsuarioAutenticado` (`{id, nome, username, papeis, professora_id,
ativo}`).
- **Import boundary:** `*.functions.ts` bundle to the browser. `auth.server.ts` must be
  `await import()`-ed inside the handler, exactly like `client.server` already is
  (`docs/framework/coding-standards.md` → Imports).
- Do not add role checks here — that's Story 1.3. This story only proves identity.
- `presenca.functions.ts` handlers currently start straight at `const client = await
sb();` — the guard goes above that line.
- Server functions that return `{ ok: false, erro }` style: throwing from the guard is
  fine; the client already surfaces thrown errors via React Query.

### Completion Notes List

- **Guard placement — deliberate deviation from AC1's literal "first statement of the
  handler":** the guard lives in each file's single DB-client helper (`admin()` /
  `sb()` / `publicClient()`), not repeated in 39 handlers. Rationale: every handler
  already `await`s its helper before touching Supabase, so this covers 100% of DB
  paths and makes it _impossible_ for a future handler in these files to query
  unauthenticated — stronger than per-handler, and no risk of missing one. AC3 (the
  actual security requirement — no DB read/write when unauthenticated) is fully met.
  Flag for @architect / @qa to confirm they're happy with helper-level enforcement.
- **8 helpers guarded:** alertas `publicClient`, cadastros `admin`, calendario
  `admin`, grade `admin` **and** `publicClient`, historico `publicClient`, presenca
  `sb`, relatorios `publicClient`, usuarios `admin`.
- **AC7 → option (b):** `usuarios.functions.ts` uses
  `await requireRole(["secretaria"])` in its `admin()` helper (all 5 endpoints), so a
  logged-in `professor`/`coordenador` gets "Não autorizado. Você não tem permissão"
  and cannot manage accounts. This pulls one bit of Story 1.3 forward; 1.3 still owns
  the rest (grade edits, cadastros, calendário role checks).
- **`auth.functions.ts` untouched** except a comment on its `admin()` helper stating
  why it stays unguarded.
- **Verification done:** `tsc --noEmit` ✅, `eslint` on all 9 changed files ✅,
  `npm run build` ✅ (client bundle does not include `auth.server.ts` — the lazy
  import boundary holds).
- **Verification NOT done (deferred to @qa):** runtime proof that (a) a logged-out
  RPC call is rejected with no DB access, and (b) a logged-in user's screens/reports
  still work (no over-guard regression). Blockers: no non-prod Supabase; dev-mode
  server-fn IDs differ from the build so raw curl can't hit them; and the Story 1.1
  gate means the UI never issues an unauthenticated RPC to observe. The guard shares
  the exact `usuarioDaSessao` → `getAuthSession` path that `getSessaoAtual` uses, and
  Story 1.1 proved that path works at runtime (SSR bootstrap form rendered). This is
  the same authenticated-walkthrough gap already logged as QA-1.1-02 — one walkthrough
  on a non-prod DB covers 1.1 + 1.2 + this story.
- **Regression risk assessment:** low. The guard only _adds_ a `requireAuthenticated`
  call at the top of the helper; a logged-in user (guaranteed present after Story 1.1)
  passes it and everything downstream is byte-identical to before.
