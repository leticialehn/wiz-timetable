## Story

**As a** deployment owner,
**I want** `SESSION_SECRET` confirmed set and cryptographically strong in the Vercel
production environment, and that fact documented,
**so that** the session cookie that gates every route and server function
(Stories 1.1–1.3) cannot be forged or brute-forced, and the next person touching
deploys knows this variable exists and why it matters.

## Acceptance Criteria

1. `SESSION_SECRET` is confirmed present in Vercel's **Production** environment
   variables for this project (via `vercel env ls production` or the Vercel
   dashboard) — not just in local `.env`.
2. The value is confirmed strong: at minimum 32 bytes of high-entropy randomness
   (e.g. `openssl rand -base64 32` or equivalent), not a short/guessable/default
   string. If the current value does not meet this bar, generate a new one and
   update it in Vercel (Production **and** Preview, so preview deployments do not
   silently share or fall back to a weak secret) — this **will invalidate all
   existing sessions**, forcing every logged-in user to log in again; call this out
   explicitly when rotating.
3. `SESSION_SECRET` is added to `.env.example` (currently missing — confirmed by
   inspection; only `SUPABASE_*` / `VITE_SUPABASE_*` keys are listed there today) as
   a documented placeholder, e.g. `SESSION_SECRET=` with a comment pointing at
   `auth.server.ts`'s `sessionConfig()`.
4. `docs/framework/tech-stack.md` documents `SESSION_SECRET`: what it is
   (password for the `escola-auth` `useSession` cookie, PBKDF2-backed encryption via
   `@tanstack/react-start/server`), where it must be set (Vercel Production +
   Preview env vars, plus local `.env`), what happens if it's missing (`auth.server.ts`
   throws `"SESSION_SECRET não configurado"`; per Story 1.1's fix, `__root.tsx`'s
   `beforeLoad` catches this and falls back to showing the login screen rather than a
   500 — but every request still fails auth until the variable is set), and the
   strength requirement from AC2. This satisfies epic AC8 (`SESSION_SECRET`
   confirmed set and strong in Vercel; documented in
   `docs/framework/tech-stack.md`) — the file already exists (created during
   brownfield discovery), so this story adds a section to it rather than creating it
   from scratch. **Corrected by @po 2026-09-14:** `tech-stack.md` contains **zero**
   occurrences of `SESSION_SECRET` today (verified by grep); the "Runtime targets"
   env-var row that lists it is in `docs/architecture.md` (line 53), a different file.
   Treat AC4 as _adding the first mention of `SESSION_SECRET` to `tech-stack.md`_,
   not as expanding an existing one. While there, add `SESSION_SECRET` to
   `tech-stack.md`'s "Runtime targets" env context too, so the two docs agree.
5. The verification steps and result (present/absent, rotated or not, date checked)
   are recorded in this story's Completion Notes and in `docs/estado.md`'s
   EPIC-001 table, so the check is auditable without re-running it.
6. No application code changes in this story — it is a config-verification +
   documentation story only.

**What to check for:**

- AC1 passes if `SESSION_SECRET` appears in **both** `env ls production` and
  `env ls preview`.
- AC2 passes if the pulled value looks like `openssl rand -base64 32` output:
  `len` ~44 (or >= 43), `unique` roughly 30–40, `looksBase64: true`. A low `unique`
  count relative to `len`, or `looksBase64: false` with dashes/words, means it is a
  human passphrase → **rotate**.
- If rotating: `vercel env rm SESSION_SECRET production` then
  `vercel env add SESSION_SECRET production` (paste `openssl rand -base64 32`
  output), and repeat for `preview`. **This logs out every active user** — announce
  it first. No redeploy of application code is required.

### Signal worth acting on

If Vercel was seeded from the same source as the local file, **AC2 will very likely
fail and a rotation will be required.** Plan for the forced-logout side effect.

## Dev Notes

- **Ground truth for what this variable does**, from `src/lib/auth.server.ts`:
  ```ts
  function sessionConfig() {
    const password = process.env.SESSION_SECRET;
    if (!password) throw new Error("SESSION_SECRET não configurado");
    return {
      password,
      name: "escola-auth",
      maxAge: 60 * 60 * 24 * 7,
      cookie: { httpOnly: true, secure: true, sameSite: "lax", path: "/" },
    };
  }
  ```
  This is the encryption password for `@tanstack/react-start/server`'s
  `useSession()` — every request's `escola-auth` cookie is encrypted/decrypted with
  it. A weak or leaked secret lets an attacker forge a valid session cookie for any
  `usuarioId`, bypassing every guard added in Stories 1.1–1.3.
- **Fail-closed behavior already shipped** (Story 1.1, `src/routes/__root.tsx`):
  if `getSessaoAtual()` throws (which it will if `SESSION_SECRET` is unset), the root
  `beforeLoad` catches it and renders the login screen instead of crashing the whole
  app with a 500. This story is about the secret being _set and strong_, not about
  the missing-secret failure mode, which is already handled defensively.
- **`docs/framework/tech-stack.md` already exists** — it is the file referenced by
  epic AC8, created during the brownfield discovery documented in `docs/estado.md`.
  **Correction (@po, 2026-09-14):** the draft claimed this file "already references
  `SESSION_SECRET` once in passing (Runtime targets table)". That is **not accurate** —
  `grep -n "SESSION_SECRET" docs/framework/tech-stack.md` returns nothing. The env-var
  row that lists `SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, SUPABASE_PUBLISHABLE_KEY,
SESSION_SECRET` lives in `docs/architecture.md:53`. `tech-stack.md`'s own "Runtime
