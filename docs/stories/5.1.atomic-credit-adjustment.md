# Story 5.1: Atomic credit adjustment (fix race condition)

## Status

Ready

## Executor Assignment

executor: "@dev"
quality_gate: "@architect"
quality_gate_tools: [coderabbit, typecheck, lint]

## Story

**As a** secretaria/professora relying on `alunos.creditos` being correct,
**I want** the credit adjustment on a presença transition to be a single atomic
database operation,
**so that** two near-simultaneous writes for the same aluno (two tabs, a retry
after a slow response) can't silently lose one credit adjustment.

## Acceptance Criteria

1. `ajustarCreditos` (`src/lib/presenca.functions.ts:24`) no longer does a
   `SELECT creditos` followed by an `UPDATE creditos = <read value> + delta` as
   two separate round trips. The adjustment becomes a single atomic operation —
   a Postgres function (`increment_creditos(aluno_id uuid, delta int)` or similar,
   called via `client.rpc(...)`) doing `UPDATE alunos SET creditos = creditos +
delta WHERE id = aluno_id AND creditos IS NOT NULL` server-side, since
   `supabase-js`'s query builder has no way to express `column = column + $n` in
   a single `.update()` call.
2. A new, named migration adds the Postgres function. It is idempotent to apply
   (standard `CREATE OR REPLACE FUNCTION`) and touches no other function, table,
   or constraint.
3. The existing `if (!aluno || aluno.creditos === null) return;` early-exit
   behavior (don't touch credits for alunos where `creditos` is `null` — i.e. not
   a credit-tracked aluno) is preserved via the function's `WHERE ... AND
creditos IS NOT NULL` guard, not a separate application-side check before the
   RPC call (that would reintroduce the same read-then-write race on the guard
   itself).
4. Every existing call site of `ajustarCreditos` (grep `presenca.functions.ts`
   for its callers — confirm the exact count and call sites at implementation
   time, don't assume) continues to behave identically for the normal
   (non-concurrent) case: presença transition into "presente" still decrements
   by 1, transition out still increments by 1, no double-adjustment on a
   same-status re-save.
5. `npm run typecheck` and `npm run lint` pass. `supabase migration list` shows
   no drift after applying.

## Dev Notes

- **Grounded 2026-09-18** by reading `presenca.functions.ts:24-35` in full — the
  exact read-then-write pattern quoted in AC1 is copied verbatim from the current
  code, not paraphrased. **Re-confirmed in PO validation:** all 3 call sites of
  `ajustarCreditos` are inside `setPresenca` (lines 80, 102, 104), each guarded
  by a status-transition check, matching AC4's claim exactly.
- **No existing `.rpc()` call anywhere in `src/`** (`grep -rn "\.rpc(" src/`
  returns nothing) — this story introduces the codebase's first Supabase RPC
  call. Not a blocker, just means there's no existing local pattern to copy;
  follow `supabase-js`'s standard `client.rpc(name, params)` shape.
- **Why an RPC, not a client-side retry/optimistic-lock**: `supabase-js`'s
  `.update()` only accepts literal values, not SQL expressions referencing the
  current column value — there's no way to express `creditos: creditos + delta`
  in the query builder itself. A Postgres function is the standard, minimal fix;
  an application-side retry loop would still have a race window between the
  retry's read and write, just a smaller one.
- **Not in scope**: wrapping the presença write + credit adjustment in a single
  DB transaction (the "crash between the two leaves them out of sync" half of
  the original DB-AUDIT note). That's a separate, larger concern — the presença
  write and credit adjustment are currently two independent server calls in
  `setPresenca`'s handler; making them transactional would likely also need an
  RPC/stored-procedure approach, which could be a natural Story 5.3 if the owner
  wants it, but doubles this story's scope if bundled in.
