## Story

**As a** maintainer,
**I want** the dead Supabase-Auth middleware removed instead of left wired into
every server function call,
**so that** the codebase has one auth story (the custom `usuarios` session cookie),
not a second, unused, and confusing one.

## Acceptance Criteria

1. `attachSupabaseAuth` (`src/integrations/supabase/auth-attacher.ts`) is deleted and
   its registration in `src/start.ts` (`functionMiddleware: [attachSupabaseAuth]`) is
   removed — not stubbed, not repurposed. **Rationale, recorded per Article
   IV (No Invention):** the epic's AC7 allows "removed or repurposed to forward the
   session cookie," but the session cookie (`escola-auth`, set by
   `getAuthSession()`/`useSession` in `auth.server.ts`) is already an `httpOnly`
   same-origin cookie — the browser attaches it to every same-origin `fetch`
   automatically, with no middleware needed. `requireAuthenticated()` already reads it
   successfully in every guarded endpoint (proven in Stories 1.1–1.3, all Done).
   `attachSupabaseAuth` attaches a **Supabase Auth** bearer token
   (`supabase.auth.getSession()`) that nothing on the server ever checks or accepts —
   there is no "forward" work left to do; removal is the correct reading of AC7, not
   a scope reduction.
2. `src/integrations/supabase/auth-middleware.ts` (`requireSupabaseAuth`) is also
   deleted. This is a second, previously-undiscovered dead Supabase-Auth artifact
   found while grounding this story: it is exported but never imported or registered
   anywhere in `src/` (confirmed by grep). It validates a Supabase JWT via
   `supabase.auth.getClaims(token)` — the same unused auth model as
   `attachSupabaseAuth` — and its removal is in scope for this story's "session
   hygiene" half of the title, alongside AC1.
3. `src/integrations/supabase/client.ts` (the anon/publishable-key client) is **not**
   touched — it is still imported live by `src/hooks/use-realtime-grade.ts` for
   Realtime subscriptions, which is unrelated to auth.
4. After removal, `grep -r "attachSupabaseAuth\|requireSupabaseAuth" src/` returns no
   matches.
5. No behavioural change for a logged-in user: login, logout, route guards
   (Story 1.1), `requireAuthenticated()` (Story 1.2), and `requireRole()` (Story 1.3)
   all continue to work exactly as before, because none of them depended on either
   deleted middleware.
6. `npm run typecheck` and `npm run lint` pass; pre-commit hook green; `npm run build`
   succeeds (Nitro/Vercel bundle) with no dangling import errors from the deleted
   files.

## Dev Notes

**[AUTO-DECISION]** Epic AC7 says "removed or repurposed to forward the session
cookie" → chose **removed** (reason: the session cookie is already forwarded
automatically by the browser as an `httpOnly` same-origin cookie; there is nothing
left to "forward" via middleware, confirmed by reading `auth.server.ts` and the fact
Stories 1.1–1.3 already work without any cookie-forwarding middleware).

**[AUTO-DECISION]** Scope also includes deleting `auth-middleware.ts`
(`requireSupabaseAuth`), which the epic text doesn't name → included (reason: it is
the same class of dead Supabase-Auth scaffolding as `attachSupabaseAuth`, confirmed
unused anywhere in `src/` by grep, and the story's own title says "session hygiene,"
not just "remove attachSupabaseAuth" — leaving one dead auth middleware while
removing its twin would be an incomplete hygiene pass).

- **Session mechanism (ground truth, `src/lib/auth.server.ts`):** `getAuthSession()`
  wraps `@tanstack/react-start/server`'s `useSession<AuthSession>({ password:
process.env.SESSION_SECRET, name: "escola-auth", maxAge: 7 days, cookie: {
httpOnly, secure, sameSite: "lax", path: "/" } })`. This is a signed/encrypted
  httpOnly cookie read directly from the incoming request on the server — no client
  middleware is involved in sending it; the browser does that automatically for
  same-origin requests. `usuarioDaSessao()` reads `session.data.usuarioId`, loads the
  user via the service-role client, and returns `UsuarioAutenticado`.
  `requireAuthenticated()` / `requireRole()` build on top of that. None of this reads
  an `Authorization` header.
- **Why `attachSupabaseAuth` was a no-op (confirmed by reading the file):** it calls
  `supabase.auth.getSession()` — the browser-side **Supabase Auth SDK** session,
  which is never populated because the app never calls `supabase.auth.signIn*`
  anywhere (login is `POST /_serverFn` to the custom `login` server function, which
  writes `usuarioId` into the `escola-auth` cookie, not into Supabase Auth). So
  `token` is always `undefined` and the middleware always sends `headers: {}` — pure
  overhead on every server-fn call.
- **Second dead file found during grounding, not previously tracked in the epic:**
  `src/integrations/supabase/auth-middleware.ts` exports `requireSupabaseAuth`, a
  `.server()` middleware that expects a `Bearer <jwt>` header and validates it via
  `supabase.auth.getClaims(token)`. It is never imported by any route, `*.functions.ts`,
  or `start.ts` — confirmed by `grep -rn "auth-middleware\|requireSupabaseAuth" src/`
  returning only its own definition. Both files carry the header comment `// This
file is automatically generated. Do not edit it directly.` — they are leftover
  Lovable Cloud/Supabase-Auth scaffolding from before the custom `usuarios` auth
  system was built, matching `docs/architecture.md` §9's "Dead code paths" finding
  (`LoginForm`, `usuarios.functions`, `attachSupabaseAuth`, ...) and
  `docs/TECHNICAL-DEBT-REPORT.md`'s item 8. The "Do not edit" comment is scaffold
  boilerplate, not a live-generation pipeline — no build step regenerates these
  files (confirmed: no reference to either filename in `package.json` scripts or
  `vite.config.ts`), so deleting them is safe and permanent.
- **Do not touch:** `src/integrations/supabase/client.ts` (anon key, used by
  `use-realtime-grade.ts`) and `src/integrations/supabase/client.server.ts`
  (service-role key, used everywhere in `*.functions.ts`/`*.server.ts`). Both are
  live and out of scope.
- **`errorMiddleware` in `start.ts` is unrelated** — it's a `requestMiddleware`, not
  `functionMiddleware`, and has nothing to do with Supabase Auth. Do not remove it.
