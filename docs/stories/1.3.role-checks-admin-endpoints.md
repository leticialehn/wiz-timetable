## Story

**As a** coordenador or professor,
**I want** to be blocked from admin-only actions (editing the grid, cadastros,
calendário, users),
**so that** only the secretaria can change the school's configuration, while I can
still run my classes.

## Acceptance Criteria

1. After Story 1.2, these mutations additionally call `await
requireRole(["secretaria"])`: all writes in `cadastros.functions.ts`,
   `calendario.functions.ts`, `usuarios.functions.ts`, and **all 6** grid-editing
   writes in `grade.functions.ts`: `setHorarioConfig`, `removerHorarioConfig`,
   `alternarVagaFechada` (all three write `horarios_config`), and `adicionarAluno`,
   `removerCelula`, `alternarAusenciaAvisada` (write `grade_base` /
   `excecoes_semana`).
2. Read endpoints and all `presenca.functions.ts` writes (presença/notas/lições) stay
   at `requireAuthenticated()` only — any papel may launch class records.
3. `alertas.functions.ts`: read endpoints require auth; the professora-scoped alert
   queries filter to `usuario.professora_id` unless **`usuario.papeis` (the login
   role, from `usuario_papeis`)** includes `coordenador` or `secretaria`. This is the
   authorization source of truth for this AC — it is a deliberate, separate check from
   the `professoras.coordenadora` boolean (the per-professora flag documented in
   `types.ts`, used elsewhere for UI-level "vê funções extras" copy). The two are not
   required to stay in sync; do not read `professoras.coordenadora` for this check.
4. A `professor`/`coordenador` session calling an admin-only endpoint gets
   `"Não autorizado. Você não tem permissão para esta ação."` and no DB change.
5. The admin nav / buttons are hidden or disabled for non-secretaria users (defense in
   depth; the server check is the real gate).
6. Checklist of endpoint → required role added to the Dev Agent Record.
7. `npm run typecheck` + `npm run lint` pass; pre-commit green.

## Dev Notes

- `requireRole(papeis: Papel[])` is in `auth.server.ts`: calls
  `requireAuthenticated()` then throws unless `usuario.papeis` intersects `papeis`.
  `Papel = "secretaria" | "professor" | "coordenador"`.
- `usuario.professora_id` links a login to a `professoras` row (nullable, `UNIQUE`).
  Never trust a `professora_id` from the request body for authorization — read it from
  the session `usuario`.
- `types.ts` documents the coordenadora exception: "Coordenação vê funções extras
  (hoje: alerta de faltas consecutivas) que as demais professoras não veem."
- Grid editing lives in `grade.functions.ts`; class-record writes live in
  `presenca.functions.ts` — the split maps cleanly to secretaria vs any-papel.
- Keep changes minimal and mechanical; no refactor of the functions' internals.

### Reviewed By: Quinn (@qa)

Verified by direct code inspection (full diff read, not the dev's self-report):
all 14 newly-gated endpoints (`cadastros.functions.ts` ×6, `calendario.functions.ts`
×2, `grade.functions.ts` ×6) call `requireRole(["secretaria"])` as the literal first
statement of the handler, before any Supabase client call. `usuarios.functions.ts`
confirmed untouched (already gated since Story 1.2 AC7) and `presenca.functions.ts`
confirmed untouched (AC2). `alertas.functions.ts`'s professora-scoping (AC3) reads
`usuario.professora_id` only from the session — `getAlertasAtivos` takes no request
input at all, so there is no spoofing surface. Fails closed when `professora_id` is
null. Independently re-ran `npm run typecheck` (clean) and scoped `eslint` on the 5
touched files (clean, exit 0) — full-repo `npm run lint` still hangs in this
session, confirmed as a pre-existing environment issue (also killed background tasks
for low memory earlier), not caused by this diff.

Two things worth recording precisely: (1) AC5's actual scope is narrower than what
Story 1.2's gate (QA-1.2-03) predicted — only the "Wizard" nav entry point is hidden,
not every direct-URL path into `/admin/*`; (2) `getAlertasAtivos` now does a second,
redundant session lookup on top of the one `publicClient()` already does, compounding
the performance finding already open from Story 1.2 (QA-1.2-01).

The runtime walkthrough (AC4) was attempted this session with 3 real test users and a
running dev server, but blocked by a Chrome automation tool failure unrelated to the
app (confirmed independently against `google.com`/`example.com` too, after a Chrome
restart and a memory check). This is the same open gap carried from Stories 1.1 and
1.2 — not a defect in this story's code.
